# flutter_ui_lints — design

## Goal

A reusable `custom_lint` package, published in `my-libs` alongside
`cubit_ui_flow_lints`, that enforces design-system discipline in Flutter
`lib/presentation/` code via `flutter analyze` / `dart analyze` (custom_lint
registers as an analyzer plugin, so no separate CLI invocation is needed).

This is a new package build only. Wiring it into pocketcoder (adding the
dependency, deleting the now-redundant checks in `theme_discipline_test.dart`)
is an explicit follow-up, not part of this plan.

## Package

- Location: `my-libs/flutter_ui_lints` (new directory, new git repo — same
  shape as `my-libs/flutter_cubit_ui_flow/cubit_ui_flow_lints`).
- `pubspec.yaml`: `analyzer`, `custom_lint_builder`, `meta` — same deps/style
  as `cubit_ui_flow_lints`.
- `lib/flutter_ui_lints.dart`: `createPlugin()` returning a `PluginBase`
  that registers all rules below, each a `DartLintRule` subclass matching the
  existing hand-written-AST-rule style (no shared base class beyond what's
  needed — see `cubit_ui_flow_lints`'s `_PathImportRule` for the level of
  abstraction to match).

## Configuration

Each rule reads its own options from `CustomLintConfigs`/`analysis_options.yaml`
at plugin-construction time (`getLintRules(CustomLintConfigs configs)` — the
same signature `cubit_ui_flow_lints` already declares but doesn't use) and
passes them into its rule's constructor, since `DartLintRule.run()` itself
has no access to config. Two rules (`no_hardcoded_font_size`,
`no_hardcoded_padding`) are plain bans with no config; the other five take
a configurable class-name list. Defaults match pocketcoder's current
design-system names, cross-checked against `app_sizes.dart`, `spacers.dart`,
`app_palette.dart`, `text_role.dart`, and the exact regexes in
`theme_discipline_test.dart` (not just its prose) during brainstorming.

```yaml
custom_lint:
  rules:
    - no_hardcoded_colors:
        banned_types: [Colors, AppPalette]
    - no_hardcoded_font_size: true
    - no_hardcoded_font_family:
        allowed_types: [AppFonts]
    - no_raw_sizedbox_spacing:
        allowed_enclosing_classes: [VSpace, HSpace]
    - no_hardcoded_padding: true
    - no_inline_widget_composition_in_pages:
        page_suffix: "Screen"
        widget_dir_names: [widgets, adapters]
        banned_widget_names: [Padding, Column, Row, Container, SizedBox,
          Text, Icon, Stack, ListView, GridView, Align, Center, Expanded,
          Flexible, Card, Scaffold, AppBar]
    - no_hardcoded_strings:
        allowed_types: [MessageKey]
```

## Rules

1. **`no_hardcoded_colors`** — a ban list, not an allowlist substitution:
   flags `Color(0x...)` construction outright, plus static access on any
   configured `banned_types` prefix (default `Colors`, `AppPalette` — the
   existing test bans `AppPalette.` too, since presentation code is meant to
   go through semantic roles like `TextRole`/`SectionState`/`ActionKind` or
   `context.colorScheme`, never the palette directly).

2. **`no_hardcoded_font_size`** — no config: flags any `fontSize:` named
   argument, unconditionally. Matches the existing test exactly — there is
   no allowed substitute at the presentation layer at all, since text size
   is meant to come from `TextRole`/`AppSizes.fontBody`, never written by
   hand.

3. **`no_hardcoded_font_family`** — allowlist substitution: flags any
   `fontFamily:` argument whose value isn't `<Type>.<member>` (optionally
   scaled by a literal multiplier) for an allowed type (default `AppFonts`).

4. **`no_raw_sizedbox_spacing`** — flags `SizedBox(height: ...)` /
   `SizedBox(width: ...)` constructor calls, except when the enclosing class
   declaration's name is in `allowed_enclosing_classes` (default `VSpace`,
   `HSpace` — matching `spacers.dart`, which is exactly where such calls are
   expected to live and nowhere else).

5. **`no_hardcoded_padding`** — no config: flags any raw numeric literal (or
   negated numeric literal) passed to `EdgeInsets.all/only/symmetric(...)`.
   A literal scaled by a token member (`AppSizes.space * 2`) is a
   `BinaryExpression`, not a literal, so it is never flagged by this
   check — no allowlist is needed, the same way `no_hardcoded_font_size`
   needs none.

6. **`no_inline_widget_composition_in_pages`** — a ban list, structurally
   scoped: for any class whose name ends in the configured `page_suffix`
   (default `Screen`) in a file that is not inside a directory named one of
   `widget_dir_names` (default `widgets`, `adapters`), flags any
   widget-constructor call inside `build()` whose type name is in
   `banned_widget_names` (default: common raw layout/content widgets —
   `Padding`, `Column`, `Text`, etc.). Provider/DI wiring widgets
   (`MultiBlocProvider`, `BlocProvider`, ...) and any custom
   extracted-widget/adapter class are never on the ban list, so they pass
   through untouched — the rule only catches hand-rolled layout, not
   composition of named widgets. The `widgets/`/`adapters/` directories are
   exempt since that's where those banned constructs are expected to live.

7. **`no_hardcoded_strings`** — matching pocketcoder's `client/CLAUDE.md`
   rule ("Never hardcode user-facing strings" / `MessageKey` for
   programmatic string lookups): flags any `StringLiteral` (a plain,
   interpolated, or adjacent-strings literal — the analyzer AST's common
   supertype for all three) passed as the first positional argument to
   `Text(...)`'s unnamed constructor. The `allowed_types` config (default
   `MessageKey`) exists for parity with the other allowlist rules and to
   name the intended replacement in the lint message, but a
   `MessageKey.someKey` reference is a `PrefixedIdentifier`, never a
   `StringLiteral` — so unlike `no_hardcoded_font_family`, there's no
   separate token-expression check to write: being a `StringLiteral` at all
   is already sufficient to flag. Scoped to `Text(...)` only, not
   `Text.rich(...)` — that constructor's first argument is a `TextSpan`,
   not a string, so this check doesn't apply to it.

## Testing

The package gets its own `test/` with one fixture pair (good + bad) per
rule, run through `custom_lint`'s test harness. Check whether
`cubit_ui_flow_lints` has an existing test harness to follow the same
pattern; if it has none, this package still needs one — recording the intent
here so the plan doesn't skip it for lack of precedent.

## Out of scope

- Adding the dependency to pocketcoder's `pubspec.yaml`/`analysis_options.yaml`.
- Deleting/trimming the overlapping checks in `theme_discipline_test.dart`
  (explicitly deferred by the user — keep that test file untouched for now).
- Building the actual `VSpace`/`HSpace` widgets for any project that lacks
  them (pocketcoder already has them in `spacers.dart`; other consumers are
  not this plan's concern).
- The other, unrelated checks already in `theme_discipline_test.dart`
  (PocoPosture naming, body-centering, scroll-view hand-rolling, bracket
  glyphs in Text) — not part of this lint package's rule set.
